# Luthor daemon architecture

## Purpose and boundary

Luthor is a small Rust daemon that discovers eligible GitHub issues, assigns them, creates daemon-owned worktrees, and runs a configured headless CLI agent until it can verify an open pull request (PR). The first agent target is `llxprt-code-rs`. The agent does the software work; Luthor owns selection, local supervision, evidence, and operator controls. Luthor does not reuse Luther or llxprt-jefe state or directories.

V1 stops at a verified open PR. Draft PRs and failing or pending checks count; show checks without using them as a completion gate. A successful agent exit alone never completes a task. There are no automatic retries, code reviews, repairs, feedback loops, merges, or unassignments. A stopped or failed attempt with no verified PR waits for an explicit operator decision. Luthor must not automatically select another eligible issue as a replacement for a held task beyond the configured capacity and source rules.

## Components and authority

- **Coordinator:** The sole local dispatcher for one state directory. It owns discovery, selection, capacity reservations, task transitions, worktrees, claim verification, and PR verification.
- **Detached supervisor:** A mode of the same executable that owns one agent child and its process group, captures stdout and stderr, waits for the child, and writes an exit receipt. It survives coordinator restarts.
- **Local control CLI:** Reads status and logs and sends `pause`, `resume`, and `reconcile` requests to the coordinator. It never independently launches an agent or writes to GitHub.
- **GitHub adapters:** Read Project items, issue details, and PR details using structured responses. The claim adapter performs one assignment write followed by independent reads. Adapter subprocess exit codes and text messages are not substitutes for verified GitHub state.

A local interprocess lock and transactional SQLite reservations prevent two coordinators using the **same state directory** from dispatching the same task or oversubscribing slots. GitHub issue assignment has no compare-and-set operation for “still unassigned and eligible.” Another state directory, Jefe, or a human can race with Luthor. Assignment plus a subsequent read cannot prove an exclusive claim. V1 requires one authorized dispatcher for each source and a policy that other actors will not assign selected issues during claim; it detects visible conflicts and stops, but does not promise race-free claims across independent actors. If exclusivity is required despite competing dispatchers, a separate atomic claim service or exclusive queue is necessary before live dispatch.

## Configuration and issue selection

JSON configuration defines private state and worktree roots, a global concurrency limit, source definitions, tracker-repository-to-code-repository mappings, code checkouts and push/head contexts, the agent executable contract, and GitHub read/write adapters. Use executable plus argument arrays, not shell interpolation. Keep credentials in the invoking user's configured credential store or restricted environment, not JSON, prompts, event records, or command-line tokens. Store a revision of the effective nonsecret configuration with each task and attempt. Changes to a source, mapping, or command do not silently change a claimed task; an operator must reconcile the change before resume.

A source specifies a Project identity, allowed issue repository or repositories, an explicit ready marker (repository label or Project field/value), and an optional exact milestone. The adapter enumerates **Project items**, then reads each referenced issue directly; it must not infer membership from `gh issue list`, a saved view, or the marker alone. Eligible means a live Project issue item, open issue, repository in scope, ready marker present with the configured value, no assignees, and, when configured, the exact milestone on that issue. A Project item's field value and a repository label are different evidence. The normalized result includes Project and item IDs, tracker repository ID and owner/name, issue node ID, number and URL, issue state, complete assignee list, marker value, milestone ID and title, and observation time. Validate these against direct reads before claiming, including item membership and readiness. Treat API omissions, permission failures, pagination gaps, non-issue items, or stale or inconsistent values as errors, not absence. Project query and field mechanics remain an external validation task.

Key tasks by stable tracker repository ID and issue node ID; show owner/name and issue number for operators. If one issue appears in multiple sources, deduplicate it and require an unambiguous source and mapping before claiming; conflicting rules hold that candidate. Persist the selected source and its evidence. Already assigned issues are not candidates, including issues previously assigned by this daemon; retained tasks, not rediscovery, govern continuation. Do not remove the ready marker when claiming. A configured milestone is part of the eligibility and acceptance evidence, not a value inferred from a label.

The tracker repository can differ from the code repository. Each mapping pins the checkout identity, target code repository, base branch, push remote and allowed head repository/account, and worktree root. Before a claim, verify that a writable checkout and a unique branch namespace can be used, and check for existing open PRs tied to the issue. A pre-existing PR is not evidence that Luthor submitted it; skip and surface it for operator attention rather than claim or count it. PRs lacking the defined issue-link marker cannot be ruled out by this lookup; acceptance must inspect selected issues for other linked PRs, and Luthor must not claim that `absent` means no PR anywhere refers to the issue. Any absent/ambiguous/error result must retain its distinction; never equate lookup failure with no PR.

## Claim and worktree ownership

Persist claim intent before a single assignment request. Re-read the issue and the Project item after the write, including on a timeout: require the expected assigned principal as the **sole assignee**, the same open issue, membership, ready marker and milestone, and direct proof that the issue now fails the source rule specifically because it is assigned. Do not use absence from a filtered discovery page as proof. A changed marker, membership, state, milestone, or another assignee is a conflict even if the candidate is no longer returned. An ambiguous write is not retried automatically. A successful read cannot establish which actor assigned the issue or exclude a later assignment race; if the single-dispatcher policy cannot be maintained, hold rather than describe the claim as exclusive. Before launch, refresh the issue and PR reads; a changed claim or existing PR blocks dispatch. After launch, record later claim changes as warnings or holds according to whether the agent is active; stop an active agent before releasing its slot if claim ownership is lost.

Use a daemon-owned worktree per task and a unique task branch from the mapped checkout and base. Persist intended path, branch and base before creation, then record the resolved worktree path and device/inode identity. Reconcile a partially created worktree and existing branch against the recorded task before reuse; never delete, reset, or adopt an unrecognized directory or branch automatically. Preserve the worktree and claim on pause or failure. A new task must not use a branch, head context, or worktree already associated with another task.

The launch prompt identifies the already claimed tracker issue, mapped code repository and worktree, expected base and head, and requires an exact `Tracker-Issue: https://github.com/OWNER/REPO/issues/NUMBER` line in the PR body. It tells the agent not to repeat assignment, even when its own skill normally does so. A prompt cannot prevent the agent from reassigning or using another credential; verify GitHub state independently. The daemon does not prescribe how the agent edits, tests, commits, or creates the PR.

## Agent executable and session contract

Configuration supplies separate initial and resume executable paths, argument arrays, working directory, private environment additions, and prompt templates. Expand only a documented set of validated task values as literal argv elements; reject malformed or missing variables and never invoke a shell for expansion. The executable runs noninteractively, has bounded adapter/startup diagnostics, and must honor the configured working directory and session arguments. Record the resolved executable, command/config revision, environment-root identity, task prompt revision, and argv shape without logging secrets. A launch is successful only when the expected child process is registered, not when a command runner merely returns success.

For the first rs configuration, generate and persist one session ID before launch. The initial and resume commands use that ID and the same resolved worktree path and config/session root (`--session ID --cwd WORKTREE -p PROMPT` for the inspected rs CLI). Preserve the root-defining environment, such as HOME and XDG variables, as well as worktree device/inode identity across attempts; reject a changed path, checkout, root, or session ID. Each resume uses a new attempt ID and a continuation prompt distinct from **all** prior prompts in that session, for example by including that attempt ID. It directs inspection of files left by the canceled turn. Only completed conversation is available from the prior session; a canceled turn's in-flight transcript is not restored. If the interrupted turn was the first, there may be no completed conversation. Do not assert that any other configurable agent supports continuation until its headless create/resume commands and state-location behavior have been demonstrated. An inability to continue is an `attention` reason, not permission to start a fresh session under the same task.

## Task state and PR evidence

SQLite retains task, attempt, slot reservation, intent, and ordered evidence records after issues drop out of discovery. Task states are `preparing`, `running`, `pause_requested`, `paused`, `held`, `attention`, and `pr_complete`. `held` means required evidence is uncertain; `attention` means the attempt is accounted for but no automatic next action is allowed. Attempt lifecycle (`launch_intended`, `starting`, `running`, `stop_intended`, `ended`, `reconciliation_required`) is separate from outcome (`exit(code)`, `signal(number)`, `launch_failed(reason)`, or an explicitly resolved telemetry loss with unavailable exit status). Never manufacture an exit code or promote an agent's zero exit to success. Every transition and lookup records stage, timestamp, source of evidence, and bounded error details.

A PR lookup must distinguish `open`, `absent`, `ambiguous`, and `error`. Its issue-link predicate is the exact `Tracker-Issue:` line with the full tracker issue URL in the PR body; validate that URL against the stored issue identity. Return `absent` only after an exhaustive, successfully paginated query of open PRs in the target code repository; incomplete search or unreadable PR details are errors. Verify PR state and immutable PR ID, target repository ID, base repository/branch, head repository ID **and** branch, and the exact issue reference. Match that to the task's persisted unique head context; a branch name alone or a generic `#number` is insufficient across repositories. Record author, creation time, PR URL, head commit, draft flag and available check summaries. Require the configured authorized PR identity and head context; if the agent uses an unexpected account or an external PR is found, hold for attention rather than counting it as Luthor's submission. The task record, claim-before-launch evidence, unique worktree/branch, attempt history, and matching PR are the auditable provenance chain. A human using the same authorized account could submit an indistinguishable PR; logs, branch history and supervised no-manual-action rules support attribution but cannot prove who used that account. An open PR detected while the agent is running triggers a stop request; after accounting for the attempt and slot, refresh issue, claim and PR evidence before setting `pr_complete`. A closed or merged PR is not an open PR under this v1 completion rule.

An accounted exit with no open PR becomes `attention`, including exit zero. A nonzero exit and an open PR remain separate visible facts; PR completion is permitted only when the PR evidence passes all checks. No task is restarted by discovery or by PR polling. `resume` is an explicit operator action on a paused or accounted task with fresh absent-PR evidence and intact claim, worktree, and session state; it is not an automatic retry.

## Process supervision and durable recovery

Reserve a slot and persist a uniquely identified launch intent in a transaction before spawning a supervisor. At startup reconcile **all** launch, claim, worktree and stop intents before any dispatch. A detached supervisor registers its attempt identity durably and starts a gated child in a new process group. It registers the child's PID, process start and boot identities and group identity before committing permission for the gate to release. On timeout, lost permission, or failed registration, the gate stays closed and the child is reaped. A coordinator crash between registration and release is resolved using persisted release evidence and a supervisor handshake; it must not issue a second launch. Supervisor and coordinator use attempt IDs and transactional state changes to prevent stale messages, duplicate receipts, or a local CLI race from creating another attempt.

The supervisor continuously drains stdout and stderr into private per-attempt files and records observed byte counts and last-output time. These live counts are not a promise that every byte survives a power loss. Before issuing a completion receipt, it flushes and syncs both logs, captures any drain/write error, waits for the child, writes and syncs a temporary receipt with attempt ID, identities, exit/signal and byte counts, atomically renames it, and syncs its directory. A log failure triggers a recorded stop and hold; never issue a clean receipt or silently discard output. A valid receipt must match the attempt and its files. Missing, corrupt, or conflicting evidence requires reconciliation. Files and directories are private to the local account; an agent running as the same user can potentially modify them, so this is crash recovery and audit evidence, not tamper-proof attestation.

A verified live supervisor retains its reserved slot across coordinator restarts. A valid receipt does **not** free a slot until the child and its process group are verified stopped; an unfinished launch or unverified group also keeps a reservation. Match identities using OS boot/start information and live supervisor handshake where possible, never a bare PID or group number. Do not signal a recycled identity. The configured agent must not daemonize or escape its process group. Portable macOS/Linux process groups cannot prove absence of an arbitrary descendant that deliberately escapes; detected escape, uncertain descendants, or a dead supervisor with a live or uncertain child holds the task and slot until independently accounted for. This boundary applies to cooperative local agents, not hostile processes. If capacity cannot be shown to be free, no task may use that slot; lower concurrency settings cannot erase existing reservations.

`pause TASK` first records stop intent, then signals only a verified group, with bounded SIGINT, SIGTERM and SIGKILL escalation and recorded evidence for each step. Confirm process termination and attempt accounting before releasing capacity. A stopped attempt with a fresh, unambiguous absent-PR read becomes `paused`; a verified PR follows the completion rule, while uncertain stop or lookup evidence becomes `held`. Keep claim, logs, worktree, session ID and exact state root. `resume TASK` requires a new fresh issue/claim read, absent-PR read, accounted prior attempt, proven-free slot and matching stored path/session identities, then reserves a new attempt. It does not recover the canceled model turn.

`reconcile TASK` refreshes evidence without launching an agent. If an exit receipt is irretrievably lost, an audited operator resolution may record `telemetry_lost` only after verified absence of registered processes and tracked descendants, inspection of claim and worktree, and a fresh PR read. Record actor, reason, time and evidence; keep exit status unavailable. If process absence or PR evidence cannot be established, remain `held` with the slot reserved as needed. Resolution never authorizes an automatic next turn. Do not present missing PIDs, silent logs, or transient GitHub errors as proof of exit or PR absence.

## Controls and diagnostic reasons

`status` shows state, latest attempt and outcome, reserved slots, last observed output age, current reason, PR URL and checks. `show TASK` shows source/mapping, issue and PR reads, ordered intents and events, process and worktree identities, and attempt outcomes. `logs TASK [--attempt ID]` shows each stream. `pause TASK`, `resume TASK`, and `reconcile TASK` use the coordinator's transitions. Silence warns without killing the agent. Reasons identify **which evidence failed and why**: source-read failure or mismatch (Project item, marker, milestone, state, assignees), claim write ambiguity or competing assignee, mapping/worktree conflict, session/path mismatch, launch/gate failure, log-write failure, agent exit or signal, stop timeout, identity/receipt/telemetry loss, PR absence/ambiguity/lookup failure, and unauthorized PR identity. Attach adapter operation, HTTP/API or OS error when available, attempt ID and evidence timestamp. Do not collapse a rate limit, missing permissions, no PR, and a malformed adapter response into the same reason.

## Security, delivery and verification limits

Run locally as one user on macOS and Linux with restricted configuration, SQLite, worktrees, logs and receipt permissions. Adapter and agent results are untrusted inputs: validate IDs, schema, repository and PR identity and bound diagnostic output. Grant only necessary Project/issue reads, assignment rights, code push rights and PR creation rights to the configured account. Verify the **currently authorized** GitHub account before live writes, including adapter and agent credentials; do not authenticate or act as the suspended `llxprt` machine account. The agent runs with the local user's authority and receives issue text from GitHub, so Luthor cannot guarantee that an untrusted issue will not induce unwanted GitHub actions. Credential isolation or stronger account scoping is a separate security boundary, not a claim of this design. Do not alter check policies or branch protection.

The first delivery is a runnable system pushed to `vybestack/llxprt-luthor`; this design document itself does not authorize implementation or a push. The subsequent acceptance target is **five distinct open PR IDs** submitted through Luthor task/attempts against `vybestack/llxprt-code`, each tied to a distinct issue in that repository with milestone `0.12.0`. Select and mark issues eligible only for supervised acceptance, before discovery; do not treat an existing Luther label, an unassigned issue, or an existing PR as sufficient. Record the configured Project/item and marker, milestone ID, initial unassigned state, claim reads, worktree/branch and attempts, authorized account, PR identity and linkage, and latest open/draft/check status for each. Count only PRs whose author and head context match configured authorization and task evidence; an agent-exit report or PR authored before dispatch does not count. No manual issue fixes or PR creation count toward this target. Acceptance of an open PR does not imply review, CI success, merge, or acceptance into the code repository.

External facts to validate before live dispatch: Project API membership, pagination, field access and ready-marker representation; assignment permissions and whether the proposed single-dispatcher policy can actually be enforced for the chosen sources; exact GitHub account and push/head permissions at acceptance; the rs headless initial/resume commands, session-root resolution, and behavior under SIGINT/SIGTERM in the installed binary. If source exclusivity cannot be enforced, record the limit and do not describe assignment as race-free; establish an atomic upstream claim before any requirement for strict cross-actor exclusivity. Exercise failed/ambiguous claim and PR reads, pre-existing and conflicting PRs, source changes, duplicate Project items, zero/nonzero/signaled exits, pause and same-session resume, partial worktrees, supervisor death, crash at every launch-gate/receipt boundary, log/disk failures, PID reuse, descendant escape, and restart with uncertain reservations. Assert that held work is never launched again and capacity is never reused without termination evidence. These are validation requirements, not results of tests already run.
