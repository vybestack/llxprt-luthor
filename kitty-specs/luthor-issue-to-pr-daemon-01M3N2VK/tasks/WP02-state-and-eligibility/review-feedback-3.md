# WP02 review: changes required

For the WP02 implementer: the read-only discovery path and SQLite reservation tests work for the covered fixtures, but the configuration and evidence boundary is not yet safe enough to approve. WP03 depends on WP02 and should rebase after the WP02 changes land. The reviewed implementation is the shared lane checkout at `.worktrees/luthor-issue-to-pr-daemon-01M3N2VK-lane-a`; this feedback changes neither WP03 nor WP04.

1. **Credential-bearing argv still passes validation and can be persisted.** `src/config.rs:224-272,309-340,353-383` identifies credentials using a finite set of option/header names and name substrings. It accepts `initial.args=["--header","PRIVATE-TOKEN: DEMO_VALUE"]`: the header is not one of the four recognized names and the string has neither `=` nor a leading `-`. I used a dummy value in ignored `tmp/wp02-independent-review/header.json` and ran `env PATH=/nonexistent ./target/debug/luthor discover --config tmp/wp02-independent-review/header.json`; it reached `Project enumeration failed: ProjectPage Transport`, proving validation accepted it without contacting GitHub. `src/state.rs:96-106,192-228` then serializes accepted argv into `selection` evidence. This violates the explicit no-credentials-in-configuration-or-state requirement (`dev-docs/config-and-state.md:3`; NFR-004). Restrict credentials-bearing option and header forms by a documented, enforceable command contract, rather than relying on a short list of token-looking names; make a test prove that the dummy `PRIVATE-TOKEN` example cannot be loaded or persisted and that errors never echo its value. Keep the external credential store/environment as the credential channel.

2. **Persisted selection evidence cannot show why an issue qualified.** `src/eligibility.rs:9-24,58-83` tests `issue.state`, complete assignees and actual label/Project field values, but `Candidate` retains none of the observed issue state, assignee list, labels or observed Project field pair. Its `marker` and `source` are copies of configured selectors, not the direct observations. `src/state.rs:218-227` persists only that candidate plus configuration; recording direct reads separately via `record_evidence` is optional (`src/state.rs:247-259`). `src/main.rs:49-67` also emits constant `state=open` and `assignees=[]` and omits tracker repository ID, URL, milestone ID and observation time even though these are available in the candidate. The design's normalized selection record requires observed state, complete assignees, actual readiness evidence, milestone ID/title and observation time (`dev-docs/architecture.md`, Configuration and issue selection). Carry the actual read evidence into the selected record and persist it atomically with the task; expose that evidence in `discover` rather than reconstructing it from assumptions. Add a test that reopens the task and verifies observed marker, state and assignees, and a CLI test asserting IDs/time/milestone are included and match the direct read.

3. **Valid same-repository PR mappings are rejected without a design basis.** `src/config.rs:212-215` forbids `allowed_pr_head_repository` from equaling either tracker or code repository. The mission and architecture require a configured, checked head repository, but do not require a fork (`dev-docs/architecture.md`, Configuration and issue selection; `spec.md`, FR-001/FR-008). Setting the documented example's allowed head to its code repository yields `invalid configuration: allowed PR head repository must be distinct from tracker and code repositories`; the dummy fixture is `tmp/wp02-independent-review/same-repo.json`. This blocks ordinary in-repository issue branches, including a valid mapping where tracker and code repository are identical. Remove that exclusion unless there is an approved explicit requirement, and test both same-repository and fork head contexts.

4. **Project field values can disappear and produce false absence.** `src/config.rs:36-39,167-175` allows an unrestricted `project_field` name/value. `src/github/project.rs:344-367` silently discards every field value typename except single-select and text. `src/eligibility.rs:109-116` then treats an empty/missing field list as an ordinary marker mismatch. For a configured field whose actual API value has a different typename, `discover` succeeds with no candidate instead of reporting an unreadable/unsupported configured marker. Validate the supported field type at configuration/source read or retain and decode every supported marker representation; otherwise return an explicit source-read error when the configured field cannot be interpreted. Test an eligible issue with an unsupported/unknown configured Project field type, including a full successful Project page, and assert it does not become a silent empty selection. Do not make unrelated Project fields fatal solely because they are present.

5. **Read error categorization loses the direct-issue operation and API failure reason.** `src/github/project.rs:156-216` maps non-JSON `gh api` failures to `Unknown` and ignores stderr; GraphQL `errors` on a successful response become `Unknown/graphql-error` (`:239-248`) without examining the error code/type. The repository metadata request inside `issue` (`:385-397`) calls `api` without attaching `DirectIssue` operation and item/issue identity, so a permission failure there is surfaced as `ProjectError::IssueRead(ProjectPage ...)` with no issue identity. This prevents the required distinction between source permission/rate-limit/transport/parse failures and their affected item (`dev-docs/architecture.md`, Controls and diagnostic reasons). Classify recognized API/GraphQL statuses/codes using bounded, secret-safe diagnostics, and attach direct-read operation and item identity to all repository and issue subrequests. Add fake `gh` cases for repository-metadata 403 and GraphQL rate-limit/permission errors; assert category, operation and item ID without echoing response bodies.
