# WP02 review: changes required

For the WP02 implementer and WP03 dependent: these findings block approval of the configuration, discovery and state foundation. WP03 should rebase after WP02 changes land. I reviewed the committed target diff against the mission spec, plan, WP02 prompt and design docs. `cargo test --offline --locked` passed (27 integration tests); `cargo fmt --all --check` and `cargo clippy --offline --locked --all-targets -- -D warnings` passed. Passing current tests does not establish the missing behavior below. No `contracts/` artifact exists.

1. **A released reservation prevents another attempt on the same task.** `src/state.rs:72,164-195` makes `task_id` the reservations primary key, marks the row `released`, then always INSERTs a new row on reserve. A second attempt with a new ID fails the unique constraint even though the slot count is zero. I reproduced the exact schema/update/insert sequence in in-memory SQLite: `UNIQUE constraint failed: reservations.task_id`. Model reservation history per attempt, with a uniqueness constraint on active reservations per task, or explicitly replace the released row while retaining durable historical attempt evidence. Add a test for reserve -> release -> reserve on one task, including restart, and assert two attempt IDs survive and only one active slot counts. This affects FR-006/NFR-001 and the specified pause/resume path.

2. **Discovery cannot supply stable task identity or the required persisted source evidence.** `src/github/project.rs:6-24,87,196-256` never fetches tracker repository node ID, issue URL, milestone ID or observation time; `src/eligibility.rs:8-21,65-99` emits only a repo name, node ID, number, Project/item ID and code repo. `src/state.rs:69-73,107-132` requires a `tracker_repo_id` that discovery does not produce and stores neither selected source/item/marker/milestone/mapping nor a nonsecret effective config snapshot; `record_evidence` is optional and independent. The design requires stable repository ID + issue node ID and auditable selection evidence before claim (FR-001/FR-002/NFR-002; `dev-docs/architecture.md`, Configuration and issue selection). Extend direct/Project reads and the candidate/task contract to carry the stable IDs, issue URL, exact marker and milestone evidence, observed-at and selected source/mapping/config revision; persist them together with task creation. Test the selected record against direct issue responses including a repository rename or mismatched ID, and verify that an accepted candidate's source evidence survives reopen.

3. **Non-issue Project items are silently treated as absence.** `src/github/project.rs:125-130` silently drops every non-`Issue` content type (including missing content type); `src/github/project.rs:286-288` silently drops an empty issue ID returned by any `ProjectReader`. The design says non-issue items, API omissions and inconsistent values are errors, not absence; a partially readable Project must not yield a confidently complete candidate set. Return a named error for non-issue/malformed membership and retain item/project identity, and add tests where an otherwise eligible Project page contains a draft/non-issue item or malformed issue reference; assert discovery errors rather than returning candidates or an empty result. If explicit exclusion of draft items is intended instead, record that deviation against the approved design before acceptance.

4. **Command configuration checks placeholders but never expands them, and credential screening is bypassable.** `src/config.rs:182-239` is only a validator; there is no production function that substitutes the allowed task values as literal argv elements or rejects missing values. `src/config.rs:146-163,188-193` allows a credential-bearing header pair, for example `--header`, `Authorization: Bearer example-secret`, because neither string matches the flag heuristic, and it checks neither the executable nor other config fields for secret material. The WP02 prompt explicitly requires validated task-value expansion without shell interpolation and exclusion of credentials from config/diagnostics. Implement a typed renderer with a complete allowlist, missing-value failure and literal single-argument substitution; constrain secret-bearing argv/header forms and document the credential boundary. Test actual rendering (including braces in substituted values, missing variables and multiple occurrences), rejected header-style credentials, and absence of secrets from errors or persisted evidence. Do not run a shell.

5. **Mapping and selected-source contracts cannot enforce the configured dispatch identity.** `src/config.rs:41-48` records tracker name, code name, checkout and base only; `src/eligibility.rs:18-21,66-91` compares only code-repository name and marker/milestone debug strings for overlapping sources. `dev-docs/architecture.md` (Configuration and issue selection) calls for push remote, allowed PR head repository/account, worktree root/checkout identity and a persisted unambiguous source/mapping. Extend validated mapping/source identity to carry those required nonsecret constraints; deduplicate using complete mapping identity and typed selectors rather than `Debug` output, retain the selected source, and test conflicting mappings/head contexts. Alternatively record a reviewed scope split if this is deliberately reserved for WP03, since WP02's configured mappings and source identity cannot currently meet the acceptance wording.

Permission failures, rate limits, malformed payloads and missing Project access cannot be distinguished in diagnostics.
